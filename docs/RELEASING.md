# Release process

Releases are development-signed previews for testing. The original app and idea are credited in CREDITS.md. Publishing a release does not imply real-device validation or a production service.

## Prepare a version

1. Check and incorporate relevant upstream commits, recording the exact revision in UPSTREAM.md.
2. Update package.json/package-lock.json and Android versionName/versionCode. Increase the Android versionCode.
3. Add docs/releases/v<version>.md and update CHANGELOG.md with concrete changes and known limitations.
4. Run relevant local checks and review the diff and attribution.
5. Push to main. The workflow runs type checks, Node/browser tests, production bundling, Android compilation and APK signature verification.
6. After successful verification, the release job creates the version tag and publishes APK, Android project ZIP and SHA256SUMS.txt as a prerelease.

GitHub Actions can also be run using workflow_dispatch on main. Pull requests build artifacts but cannot publish. Existing release versions are left intact; changes need a new version. The release job alone receives contents:write, and only for publication. No personal token or external service secret is required.

Debug keys are generated by the Android build environment. Signatures can change between runs; a test build may not install over another build signed with a different key. Production signing is a separate process with owner-controlled credentials and is not configured here.

## Verification and downloads

Review the Actions run and release assets. Download the APK and SHA256SUMS.txt, then run `sha256sum --check SHA256SUMS.txt` in a directory containing both downloaded build assets. Install on a test device, exercise Back/keyboard/audio/offline behaviour and record the actual result before claiming device compatibility.
